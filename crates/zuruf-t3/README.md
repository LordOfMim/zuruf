# zuruf-t3

Eigenständiger asynchroner Adapter, ohne Abhängigkeit auf `zuruf-core`. Öffentliche API: `src/lib.rs`.

`T3Adapter::new(cli, credentials_path)` → `connect(origin)`; alternativ explizit `connect_cli()`. `connection` entspricht `T3Connection` im Protokoll. `list_projects`, `catalog(search)`, `create_thread`, `send_message`, `thread_status`, `find_threads_by_marker`, `interrupt`, `upload_image`, `send_attachments`, `watch`, `disconnect` sind async. `watch` benötigt exklusiven Adapterzugriff; für Dispatch parallel einen zweiten Adapter mit denselben gespeicherten Credentials verbinden. Ein Watch verarbeitet viele Thread/Run-Paare über denselben HTTP-Client und dieselbe MCP-Session; Kanal-Backpressure, Stop-Kanal und exponentielle Rücknahme unveränderter Threads (max. 32 × Intervall).

Der Aufrufer legt ein privates Zustandsverzeichnis an und übergibt den Credentialpfad außerhalb des Repositories. Datei atomar 0600, keine Token-Diagnostik. Disconnect widerruft genau die eigene Session. OAuth ohne Refresh-Grant: nach Zurückweisung wird neu gepaart; Mutationen werden danach **nicht** automatisch wiederholt. Vor Retry Marker abgleichen, mehrdeutigen Ausgang manuell auflösen. Die Credentials haben hier 30 Tage Laufzeit, der Pairingcode fünf Minuten.

Origin ist ein expliziter Loopback-Seed vom Aufrufer (z. B. `T3_URL`), validiert und anschließend über `/.well-known/oauth-authorization-server` entdeckt; keine T3-Dateien werden gelesen. Eine unterstützte CLI-Origin-Discovery lieferte `t3 status --json` nicht. Keine Portsuche. HTTP-Redirects sind deaktiviert.

Minimale nachgewiesene Scopes: `orchestration:read` + `orchestration:operate`, OAuth-Entscheidung `access: approval-required`. Dieser Zugang hat eine entsprechende Runtime-Obergrenze. Höhere Modi werden vom Server abgelehnt; der Adapter erhöht Berechtigungen nicht stillschweigend. `AgentProfile` wird einschließlich Options, Runtime/Interaction und Workspace abgebildet. Projekt-ID oder exakt registrierter Workspacepfad akzeptiert. `new_worktree` erzeugt `zuruf-<requestId>`; bestehende Worktrees werden vor Providerstart gebunden. Options enthalten nur die vom Katalog gelieferten Werte verwenden.

Core-Verdrahtung: gleichnamige camelCase-Typen per serde in Core-Typen überführen. `ThreadReceipt` → Task.threadId/threadUrl/workspacePath/branch; Run-ID separat persistieren. `ThreadStatus.status` → TaskStatus, `remoteStatus`, `lastMessage`, `pendingRequest`, `error` → gleichnamige Taskfelder. Nicht auf andere Runs schließen. `idempotentLaunch=false`: Replay ist an den OAuth-Client gebunden. `attachments=true` nur bei angebotenen Prepare-/Send-Schemas, live POST getestet. `push=false`: Reconnect/Replay des zusätzlichen Effect-WebSockets ist nicht bewiesen. `watch` pollt mit Backoff; Activity wird je Abfrage paginiert gelesen, keine fortlaufende Cursor-Persistenz über Polls. CLI-Fallback unterstützt keine Katalog-/Projektliste, Modelloptionen, Moduswahl, bestehenden Worktree, Attachments oder Interrupt und lehnt nicht erfüllbare Profile ab. Markerlookup ist im MCP-Betrieb rein MCP.

Run kann trotz `completed` eine offene Benutzerfrage enthalten. Activity `approval_request` → needs_approval, `user_input_request` → needs_review. Terminaler Fehler/Abbruch gewinnt gegen alte Pending-Items. Unbekannter Run → unknown_remote_state. Die API liefert den Fehlertext des Zielruns. Ausführliche Livebefunde und Testthreadliste: `../../docs/feasibility/t3-followup.md`.
